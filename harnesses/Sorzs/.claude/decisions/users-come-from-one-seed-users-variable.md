# Users come from one SEED_USERS variable

`Users` is an interface the domain owns, with an in-memory and a SQLite implementation (`users-persist-in-sqlite-and-the-seed-only-adds-the-missing`); the password is stored hashed with `Bun.password`. The users are read from `SEED_USERS`, a comma-separated list of `username:password[:role]` pairs (`xaviuzz:p1casso:admin,ana:pueblos` in development and e2e). The role is `admin` or `user`; a pair with two fields is a `user`; any other role refuses the start. It replaces `SEED_USER` and `SEED_PASSWORD`, and the backend refuses to start without it or without `AUTH_SECRET`. Why: `src/` holds no literal credentials, and one variable grows with the users, and with a role as one more attribute of the same user, where a variable or a file per user or attribute would multiply names in every Compose file. A users file was rejected: it adds a file to mount for two users. The interface lets the SQLite store and the memory double serve the same domain, as with the page reader (`the-page-reader-is-an-interface-the-domain-owns`). Only `admin` and `user` exist; finer permissions wait for a real need. A password with a comma or a colon is not supported; the dev passwords have none. On start it only adds the users the database lacks (`users-persist-in-sqlite-and-the-seed-only-adds-the-missing`).
