# fotoAlbum decisions

## Umbrella of two repos
Backend and frontend are separate repos with separate pipelines, but one project for PrometeuZZ: `Sandbox/fotoAlbum/` is a plain directory, not a repo, with its harness in `harnesses/fotoAlbum/`. Why: cross-repo specs and decisions are tracked in PrometeuZZ, and no third repo or submodule needs maintaining.

## Short clone names
GitHub repos are `fotoAlbum-backend` and `fotoAlbum-frontend`; the clones are `backend/` and `frontend/` inside the umbrella. Why: the umbrella already gives the context.

## Each repo carries its own CLAUDE.md
Stack, commands and conventions are committed in each repo. Why: both repos are ours, and each is self-describing when opened alone. The umbrella keeps only cross-repo knowledge.

## Backend owns the contract
`openapi.yaml` lives in `backend/`. `frontend/` commits a pinned copy and generates its client from it; its pipeline fails when the generated client drifts from the copy. Why: explicit, versioned, one-way dependency, no cross-repo access in CI. Revisit with a published artifact if copying hurts.

## Pipelines and deploy deferred
GitHub Actions with the same gate (lint, test, build) in both repos is the intent, chosen together with the tooling while building the boilerplates. No deploy until there is a target. Why: the TypeScript tooling is discovered while building each boilerplate.

## RPC API, not REST
One `POST /<domain>.<action>` route per operation (first one: `/health.check`), described in `openapi.yaml`. Why: the API is a set of named calls with a structured message, not resources; one route per operation keeps OpenAPI and the generated client simple. Single `/rpc` endpoint with a discriminator was rejected: it moves routing into our code and forces `oneOf` in the contract.

## Call and Reply: header and body
Call header carries only `callId`: required, opaque, generated by the client, echoed back. The operation is the URL, not a header field. Reply header carries `callId` and `status` (`ok` or `error`); an error replaces the body with `code` and `message`. Why: smallest message that correlates calls; version, auth and timestamp wait for a real case.

## Errors live in the message
Operation failures answer HTTP 200 with `status: error`. HTTP 4xx/5xx is only for transport failures that prevent building a message: unreadable JSON or missing `callId` (400), unknown URL (404), crash outside an operation (500). First codes: `INVALID_BODY`, `INTERNAL_ERROR`. Why: one place to read the outcome of a call; domain codes arrive with the slices that need them.

## Backend tooling: Bun native plus Biome
`Bun.serve`, `bun test`, TypeScript unbuilt; Biome is the only added dependency. No HTTP framework and no validation library: body validation is hand-written inside each operation. Why: one endpoint style and one operation do not justify them. Revisit validation at three operations.

## Operations are objects behind a registry
`Operation` (name, body validation, execution) and `OperationRegistry`, which the server queries by URL. Why: adding an operation never touches the server.

## Contract conformance by correspondence test
A test compares the routes in `openapi.yaml` with the registered operations, both ways. Why: no dependency, and it catches the likeliest drift (operation added without contract, or the reverse). Revisit with response validation against the schema if body shapes diverge.

## Vertical slices, health check first
Work in vertical slices (contract, backend, frontend). The first slice is a health endpoint through to a frontend page, to prove the contract pipeline before real features depend on it.

## Empty callId counts as missing
`callId` must be a non-empty string; an empty one is rejected like an absent one. Why: an empty id correlates nothing.

## Call parse failure is an exception
`Call.from` throws `InvalidCallError`; the operation turns it into the transport 400. Why: the failure is a boundary event, not a value the rest of the code branches on.

## Unknown operation is a Null Object that serves 404
`OperationRegistry.find` always returns an `Operation`; an unknown name yields `NoOperation`, whose `serve` answers 404. Why: the server never branches on absence.

## Operations serve HTTP requests
`Operation.serve(Request): Promise<Response>`, not a Call-to-Reply call. Why: the 404 of an unknown URL is then polymorphism, and each operation owns its transport failures (400). A shared base class (Template Method) carries the common flow so operations only validate and execute.

## Backend CI gate
GitHub Actions workflow `.github/workflows/ci.yml` on push to `main` and on pull requests: frozen install, lint, typecheck, test, build, on Bun pinned to the local version. Typecheck is in the gate because `bun build` does not check types. No deploy, cache or matrix. Why: smallest gate that matches what is run by hand; the frontend repeats it and adds the generated-client drift check.

## Call and Reply, not Request and Response
The application message pair is `Call` (header `callId`, body) and `Reply` (header `callId` and `status`); the base operation class is `CallOperation`. Why: `Request` and `Response` already mean HTTP in `Operation.serve`, and "envelope" read as transport. `callId` replaces `requestId` on the wire for the same reason. `Invocation`/`Outcome` was the runner-up. The word "request" or "response" never names an application-layer concept: `InvalidRequestError` became `InvalidBodyError` and `INVALID_REQUEST` became `INVALID_BODY` (the other `Invalid*Error`, `InvalidCallError`, is the malformed-Call 400); OpenAPI schemas are `CallHeader`, `ReplyHeader`, `HealthCheckCall`, `HealthCheckReply`. HTTP `Request`/`Response` stay only at the transport edge.

## Body is an object; Call answers for itself
`Body` wraps the input fields and offers `requireText(field)`, which throws `InvalidBodyError("<field> is required")`; `InvalidBodyError` lives in `call/` beside it. `Call` keeps `callId` private and builds its own `Reply` through `ok(result)` and `failure(code, message)`. Why: tell, don't ask; no code reads raw fields or the call id to assemble a reply. `Call.runOn(operation)` (the call runs the operation, `body` private) was weighed and deferred: it makes `validate` and `execute` public and moves the error-to-code mapping into `Call`. Revisit with a second operation.

## Frontend tooling: Bun native, no Vite
Bun builds (`index.html` entry, `bun-plugin-tailwind` for Tailwind v4) and serves in dev; React, shadcn, Biome and TypeScript on top. Tests are `bun test` with happy-dom and Testing Library. Why: same runtime and runner as the backend, no second toolchain. Risk: Testing Library under `bun test` is less trodden than under Vitest; if it blocks, revisit Vitest.

## Generated client: openapi-typescript and openapi-fetch
The client is types plus a thin fetch wrapper generated from the pinned `openapi.yaml`, regenerated by `generate`; CI fails on drift. `@hey-api/openapi-ts` was rejected as heavier than one operation needs. Why: the generated part is only types.

## Dev reaches the backend through a proxy
The frontend dev server proxies `POST /health.check` to `API_URL` (default `http://localhost:3000`); the client base URL is `/`. The backend gets no CORS. Why: the browser talks to one origin and the backend stays untouched. Deploy topology waits for a target.

## Flexoki palette, light and dark
Flexoki colors fill the shadcn CSS variables, light and dark following `prefers-color-scheme`, no theme toggle; accent blue, green for ok and red for error. Why: smallest theming that honors the palette; a toggle waits for a need.

## Health mark has three states
Checking (neutral), ok (green ✓), error (red ✗). One check on page load, no polling; `status: error`, network failure and non-200 all count as error. shadcn is initialized but no component is generated: the mark is an icon with `role="status"`. Why: the neutral state avoids a false error flash; polling and extra components wait for a real case.

## Frontend skills at project level
`shadcn-ui/ui@shadcn` and `vercel-labs/agent-skills@vercel-react-best-practices` are installed in `frontend/`. No Tailwind or Testing Library skill was trustworthy enough. Why: only the two with wide adoption and an official or established source.

## React and Testing Library peers arrive in the skeleton
`react`, `react-dom` and their types are installed in step 1, not step 2, because `@testing-library/react` needs them as peers and the first test renders a component to prove the environment. Biome also skips `.claude/` and `skills-lock.json` in the frontend: installed skills are not our code. Why: lint must judge only what we write.

## Frontend build is a script, not the CLI
`build.ts` calls `Bun.build` with `bun-plugin-tailwind`; `dev.ts` serves `index.html` with Bun's HTML routes and the plugin from `bunfig.toml`. Why: `bun build index.html` ignores plugins, so Tailwind directives reached `dist/` unprocessed.

## Biome parses Tailwind directives
`css.parser.tailwindDirectives` is on in the frontend's `biome.json`. Why: `@theme` and `@apply` in `index.css` are Tailwind syntax and fail to parse otherwise.

## Frontend stays on TypeScript 5
The frontend pins `typescript@^5` while the backend runs 7.x. Why: `openapi-typescript` 7.13 peers on `typescript ^5` and calls its JavaScript API (`ts.factory`), which the native 7.x compiler does not expose. Revisit when `openapi-typescript` supports 7.x.

## Generated schema is checked by regeneration
`generate:check` regenerates `src/api/schema.d.ts` into a temp directory and compares it with the committed file; `src/api/schema.d.ts` is excluded from Biome. Why: it catches a hand-edited schema or a `openapi.yaml` copy refreshed without regenerating, with no cross-repo access.

## HealthCheck wraps the generated client; tests fake fetch
`HealthCheck` takes an `openapi-fetch` client and `run()` answers `ok` or `error`, never throwing. `HealthMark` gets its `HealthCheck` from `useHealthCheck()` and picks icon, label and color from a lookup keyed by checking, ok or error. Tests build the real client with a fake `fetch`, so the generated paths and parsing are exercised. Why: the API is faked at the network edge, the one place that carries no logic of ours.

## The API reaches components through one ApiProvider
`ApiProvider` takes `baseUrl` and an optional `fetch`, builds the `openapi-fetch` client and an `Api` holding every API client (today `healthCheck`). `main.tsx` renders `<ApiProvider baseUrl={window.location.origin}>`; components read what they need with hooks such as `useHealthCheck()`, which throw outside a provider. Tests wrap the component under test in `ApiProvider` with a fake `fetch`. Why: passing `HealthCheck` as a prop made `App` and `Header` carry a type only `HealthMark` uses, and each new API client would add another prop to the chain. The provider covers the whole API, not one client, so a new client is one line in `Api`. Creating the client inside the component or in a hook was rejected: it ties the component to the real `fetch`, so tests would need module mocks. `baseUrl` is a prop so the provider does not read `window`; `fetch` exists so tests fake the network edge.

## Frontend CI gate
Same workflow as the backend (`.github/workflows/ci.yml`, push to `main` and pull requests, Bun 1.4.3, frozen install, lint, typecheck, test, build) plus `generate:check` as the last step. Why: one gate shape in both repos; the drift check is the only addition the frontend needs.

## E2E is a third repo, composing the other two
`fotoAlbum-e2e`, cloned as `e2e/`, holds a Docker Compose that builds `backend/` and `frontend/` from sibling paths (overridable by environment variable) and a Playwright service that runs against them. CI checks out the three repos side by side. Each of `backend/` and `frontend/` owns its own `Dockerfile`; `e2e/` only composes. Why: each repo knows how to package itself, and local runs test local code without pushing. Building from GitHub URLs was rejected: it only tests what is already pushed.

## E2E covers the happy path only
Boilerplate: one test, the green health mark. A new e2e test needs a reason it cannot be proven in `backend/` or `frontend/`. Why: e2e is slow and brittle; the red and neutral marks are already covered by frontend tests with a fake `fetch`.

## E2E frontend runs the dev server
The frontend container runs `bun run dev` with `API_URL=http://backend:3000`; its proxy is the only route to the backend. Why: no new code, and no production server without a deploy target. Revisit when deploy topology is decided; e2e then tests the real topology.

## Playwright on Node in the official image
The runner is a Compose service on `mcr.microsoft.com/playwright`, version pinned equal to `@playwright/test`, running Node. Dependencies: `@playwright/test`, Biome, TypeScript. Why: Playwright on Bun is not the supported path, and the image already carries the browsers.

## Compose waits on healthchecks
Backend and frontend declare a `healthcheck`; the runner uses `depends_on` with `condition: service_healthy`. One command, `docker compose up --build --abort-on-container-exit --exit-code-from e2e`, is exposed as `e2e`. Why: no `sleep`, and the exit code serves CI.

## E2E adds @types/node
`@types/node` is a fourth devDependency of `e2e/`, with `types: ["node"]` in `tsconfig.json`. Why: `playwright.config.ts` reads `process.env.BASE_URL`, and `tsc` cannot type `process` without it. Approved by Xavier on top of the spec's three.

## E2E Compose uses host networking
Every service sets `network_mode: host`, with distinct ports: backend `BACKEND_PORT` (3100), frontend `FRONTEND_PORT` (5273), both overridable; the frontend's `API_URL` and the runner's `BASE_URL` point to `localhost`. Why: in this sandbox bridge networking fails (`operation not supported` creating the veth pair), and the host already uses 3000 and 5199. The images' own defaults (3000, 5173) are untouched. Revisit if CI or another machine needs bridge: service names would replace `localhost`.

## E2E CI gate
`e2e/.github/workflows/ci.yml` (push to `main` and pull requests) checks out `fotoAlbum-e2e`, `fotoAlbum-backend` and `fotoAlbum-frontend` side by side under their umbrella names, installs with `npm ci` on Node 26, then runs lint, typecheck and `npm run e2e` from `e2e/`. The compose keeps host networking in CI: it works on the runner and keeps one file for both. Why: same gate shape as the other repos plus the one command that exercises the whole stack. Triggering from backend and frontend pull requests is out of scope; it needs a cross-repo token.

## Album is a catalogue model
`Album` is a model in the catalogue (size, page size, page count, binding), not a physical album owned by someone; photos and layout belong to a future concrete album made from a model. Why: the product to offer and the object someone fills are different things with different lives. The concrete album has no name yet. Defined in `docs/album.md`.

## Albums are withdrawn, never deleted
An album leaves the catalogue by being withdrawn; there is no delete, and its reference is never reused. Why: concrete albums will depend on the model they came from. Whether a withdrawn album can return, appear in lists or be consulted is open in `docs/album.md`.

## Album reference is typed by the user
The reference is unique, immutable, readable (letters, digits, hyphens; case-insensitive), typed by the user, not generated. Why: Xavier's choice; the commercial name is only a label and may repeat.

## Album measures: free millimetres, no limits
Album size and page size are whole millimetres above zero with no upper limit, and a page never exceeds the album. Page count is even, with no range per binding. Bindings: hardcover and softcover. Why: no real printing limit is known yet; limits arrive with one. Format is immutable after creation, since a layout depends on it.

## First slice: choose an album
The slice lists the catalogue as cards, opens a making page for the chosen album and is covered by one e2e happy path. Spec: `specs/choose-album.md`. Why: it is the smallest path that crosses contract, backend, frontend and e2e with a real concept.

## Catalogue in memory with a seed
`album.list` and `album.get` read an in-memory catalogue seeded with three albums (square, portrait, landscape). Why: create is another slice; storage arrives with it.

## Choosing an album stores nothing
Clicking a card navigates to the making page and persists nothing. Why: the concrete album has no concept yet; its doc comes before any storage.

## react-router for two pages
The frontend adds `react-router` for `/` and `/confeccion/:reference`. Why: reload and direct links need a URL per page; state-only navigation was rejected. Approved by Xavier.

## Interface in Spanish
UI texts are Spanish; code, contract and identifiers stay English. Why: Xavier's choice.

## Album contract shape
`Album` carries `reference`, `commercialName`, `albumSize` and `pageSize` (each `{ width, height }`, whole millimetres), `pageCount`, `binding` (`hardcover` or `softcover`) and `orientation` (`square`, `portrait` or `landscape`). `album.list` answers `{ albums }`; `album.get` takes `{ reference }` and answers `{ album }` or the error `ALBUM_NOT_FOUND`. Why: sizes are pairs that always travel together, so nesting them keeps each pair one value.

## Orientation is computed before serving
The backend derives `orientation` from the album size on every reply; it is never stored or entered. Why: it follows from the size by rule, so a stored copy could drift.

## Album reference lookup ignores case
`album.get` finds `fam-2025` and `FAM-2025` as the same album and answers the reference as the catalogue holds it. Why: the reference is case-insensitive in `docs/album.md`.

## Album seed
`SQ-210` "Cuadrado clásico" (210×210, page 200×200, 24 pages, hardcover); `PT-150` "Retrato de bolsillo" (150×210, page 140×200, 20 pages, softcover); `LD-297` "Paisaje grande" (297×210, page 287×200, 32 pages, softcover). Why: one album per orientation; the e2e test relies on them.

## Album lookup takes the typed text
`Catalogue.find` takes the text typed by the caller and compares it, ignoring capitals, with each album's reference. A text that is not a well-formed reference simply matches nothing and answers `ALBUM_NOT_FOUND`; `Reference` is validated only when an album is created. `AlbumNotFoundError` is mapped to `ALBUM_NOT_FOUND` in `CallOperation`. Why: consulting needs no validation, and a malformed lookup is just an album that does not exist.

## Pages load their own data
`HomePage` and `MakingPage` each read through `useAlbums()` into their own loading, error and answer state; there is no generic loading hook. Why: two uses, with different data shapes; the rule of three comes first.

## Loading, error and empty states
Loading is a quiet "Cargando…" with `role="status"`. A failed call is a shadcn `Alert`; an empty catalogue and an unknown reference are a shadcn `Empty`. Why: loading must not look like an empty catalogue, and the project skill asks for these components over hand-made markup.

## Spanish labels for album values
Binding reads "Tapa dura" or "Tapa blanda"; orientation reads "Cuadrado", "Vertical" or "Apaisado"; sizes read "210 × 210 mm". Why: the interface is in Spanish; the contract values stay English.

## Bring the stack up for manual checks
`e2e` has `up` and `down` scripts that start and stop backend and frontend without the Playwright service, and image builds use host networking. Why: trying the web against the real backend by hand needs the same composition the tests use, and the bridge network fails in this sandbox for builds as well as services.

## Page parts live in their own components
`HomePage` and `MakingPage` only load data and compose; what they show for each state lives in `Catalogue`, `AlbumRow`, `AlbumMaking` and `AlbumCharacteristics` under `src/components/`, each with its own test. Page tests keep the first level: the title, the heading, the reference asked, the way back. Why: private parts inside a page cannot be tested on their own, and the layout rule asks for the child's content to belong to the child's test.

## Components grouped by feature
`src/components/` holds one component per file, in `layout/` (`Header`, `HealthMark`), `catalogue/` (`Catalogue`, `AlbumRow`, `AlbumCard`) and `making/` (`AlbumMaking`, `AlbumCharacteristics`); `test/components/` mirrors it. What is not a component lives in `src/lib/`. Why: what changes together lives together, and a folder of components should hold only components.

## Albums are presented by a decorator
`Albums` answers `PresentedAlbum` (in `src/lib/`), a decorator that wraps the contract `Album` and adds the Spanish labels (binding, orientation, album and page size); the components ask it and no longer know the label maps. It forwards `reference`, `commercialName` and `pageCount` and does not expose the raw `Album`. Why: tell, don't ask; the contract type is generated and cannot carry behavior, and composition beats inheritance.

## Catalogue takes half the window and fits up to three albums
The catalogue row takes half the window width and half its height. With three albums or fewer the cards share the row width and no scroll appears; with more they keep a fixed width and the row scrolls sideways. Why: Xavier's choice, so a short catalogue looks full instead of lost and a long one stays reachable.
