# Call and Reply: header and body

The application message pair is `Call` and `Reply`, never `Request` and `Response`. Call header carries only `callId`: required, a non-empty string (an empty one is rejected like an absent one), opaque, generated by the client, echoed back. The operation is the URL, not a header field. Reply header carries `callId` and `status` (`ok` or `error`); an error replaces the body with `code` and `message`. `Call.from` throws `InvalidCallError` for a malformed Call, and the transport answers it as the 400 `UnreadableCall`.

Names: `Request` and `Response` already mean HTTP in `Operation.serve`, and "envelope" read as transport; `Invocation`/`Outcome` was the runner-up. The words "request" and "response" never name an application-layer concept: `callId` replaced `requestId` on the wire; `InvalidRequestError` became `InvalidBodyError` and `INVALID_REQUEST` became `INVALID_BODY`; OpenAPI schemas are `CallHeader`, `ReplyHeader`, `HealthCheckCall` and `HealthCheckReply`. HTTP `Request` and `Response` stay only at the transport edge.

Why: smallest message that correlates calls, with version, auth and timestamp waiting for a real case; an empty id correlates nothing; a malformed call is a boundary event, not a value the rest of the code branches on, so it is an exception; the pair is named apart from HTTP so the two layers never share a word.
