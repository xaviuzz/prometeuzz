# The CLI reports service failures through one guarded call

The API wrappers (`ApiSorzs`, `ApiUsers`, `ApiSorzs`, `ApiHealth`) turn a refusal into `ServiceRefusal` and a forbidden answer (HTTP 403 or the `FORBIDDEN` code) into `ForbiddenAnswer`; `ReachableFetcher`, wrapped around the `fetch` of `AddressedClients` and `AddressedLogin`, turns a network failure (`TypeError`) into `BackendUnreachable`. All of them, with `InvalidCredentials`, extend `ReportableError`, which describes itself: `reportTo(terminal)` writes its message to the error output and `settle(session)` does nothing unless the error needs the session (`ForbiddenAnswer` makes it `expire`, which forgets the pass). Every command runs its call inside `GuardedCall`, and `Session.enter` does the same for the login: each reports the error, settles it, and rethrows anything that is not a `ReportableError`. Why: ten commands share one failure policy, so a command holds only its own output and a new one inherits the policy by using the guard; a new failure is a new subclass, not a new branch. The domain stays free of the generated client's `CallRefusedError`. Repeating the `try` in each command was rejected: ten copies of the same branches. A chain of `instanceof` in the guard was rejected: the guard asked each error what it was instead of telling it to report itself.
