# The CLI API is grouped by concept and by mechanics

`cli/src/api/` holds one folder per concept, as `domain/` does: `source` (`ApiSources`, `ApiCensus`), `user`, `session` (`ApiLogin`, `AddressedLogin`) and `backend` (`ApiHealth`). Two folders hold mechanics that cross concepts: `client` (`Clients`, `AddressedClients`, `ReachableFetcher`: where the backend is, how a call is signed, what a network failure becomes) and `answer` (`Refusable`, `ServiceAnswer`, `CallRefusedError`, `CallId`, `textOrEmpty`: how a reply is read). The generated `schema.d.ts` stays at the root. `test/api/` mirrors `src/api/`. `ApiSorzs` was renamed `ApiCensus`, since it implements `Census`.

Why: fifteen files in one level mixed three forces, adapters, client building and reply reading, and `ApiSorzs` named the whole service while serving only the census. An adapter is found by the concept it implements, the same way as in `domain/`. Grouping by technical type (`adapters/`, `plumbing/`) was rejected, as `commands/` was in [the CLI domain is grouped by concept](the-cli-domain-is-grouped-by-concept.md). `schema.d.ts` stays put so `generate` and `generate:check` keep their paths.
