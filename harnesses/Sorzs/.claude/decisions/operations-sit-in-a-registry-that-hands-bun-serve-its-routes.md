# Operations sit in a registry that hands Bun.serve its routes

`Operation` is what the server serves: a `name` and `serve(Request)`. `OperationRegistry` holds the operations by name; `OperationRegistry.standard()` is where they are assembled. Its `routes()` answers one `POST` route per operation, under `/<name>`, and `Server` hands that map to the `routes` option of `Bun.serve`; its `fetch` is only the 404 for whatever no route took. Why: adding an operation touches the registry and never the server, which then holds no dispatch of its own, and a new kind of route (a `GET` resource) joins as one more registry whose `routes()` is spread beside the operations'. `routes` is part of Bun, so it adds no dependency; Hono, Elysia, itty-router and `URLPattern` routers were weighed and added a dependency for the same dispatch. A method with no handler on a known path falls to `fetch`, so it answers 404, not 405. `Operation` does not declare its method: every operation is a `POST` (RPC API), and the first non-POST operation is the moment to add it.

Replaces "Unknown operation is a Null Object that serves 404": `find` always returned an `Operation` and an unknown name yielded `NoOperation`, so the server never branched on absence. `find` and `NoOperation` are gone.
