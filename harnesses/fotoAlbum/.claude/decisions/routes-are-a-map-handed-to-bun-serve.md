# Routes are a map handed to Bun.serve

`OperationRegistry.routes()` answers one `POST` route per operation, under `/<name>`; `ResourceRegistry.routes()` answers one `GET` route per `ResourceRoute` (a `path` and a `serve`, as `Operation` is a `name` and a `serve`); `ThumbnailRoute` is the first, under `ThumbnailUrl.PATTERN`. The name is `Resource`, not `Photo`, because routes unrelated to photos may come. `Server` spreads both into the `routes` option of `Bun.serve`, and its `fetch` is only the 404 for whatever no route took. Why: the `if` in `Server` tested the thumbnail predicate by hand, so every route with a pattern would have added another. `routes` is part of Bun, so it adds no dependency; Hono, Elysia, itty-router and `URLPattern` routers were weighed and added a dependency for the same dispatch. A method with no handler on a known path falls to `fetch`, so it answers 404, not 405; the contract is unchanged. A `GET` to an operation URL now answers 404 where it used to reach the operation. `Operation` does not declare its method: every operation is a `POST` (RPC API), and the first non-POST operation is the moment to add it. `ThumbnailRoute.serve` still validates from `request.url`, so an unsafe session or a malformed id answers 404 as before.

Replaces [Unknown operation is a Null Object that serves 404](unknown-operation-is-a-null-object-that-serves-404.md): `find` and `NoOperation` are gone. Replaces the line in [Transport is separate from operations](transport-is-separate-from-operations.md) that keeps `ThumbnailRoute` outside the registry: it now lives in its own registry, symmetric to the operations one. A common interface over both registries waits for a third source of routes.
