# Migrations are numbered steps written by hand

The schema of `sorzs.db` changes through an ordered list of migrations, one class per file in `infrastructure/sqlite/migrations/`. `Migrations` reads `PRAGMA user_version`, applies each later migration in its own transaction, sets the version inside that transaction, and `MigratedDatabaseFactory` opens `sorzs.db` and runs it, once in `Server.start`, before the repositories receive the connection. A failed migration rolls back and stops the start; a version above the last known one stops it too. Repositories take the migrated connection, assume the schema and no longer create or alter tables. Migrations go forward only, and the user seed stays in `SqliteUsers` because it is configuration applied on every start. The first four migrations tolerate a state already applied, so databases saved before the versions existed (all at 0) land on 4.

Why: the migrations were functions inside the repositories that run on every start, with no record of what was applied, no order across the two tables of one file, and no way to reason about a deployed database. `user_version` is built into SQLite, so one integer per file replaces a tracking table. A library was weighed and rejected: the small ones (`bun-sqlite-migrations`, `migralite`, `bun-migrate`) are little more than this loop, have little use or maintenance, and the file-based ones run only SQL, while `RenameOldIdentifierKey` rewrites JSON documents. Hand-written code adds no dependency and each migration is testable from the previous state. A newer database is refused and a failed migration is whole-or-nothing for the same reason as the unreadable file: fail fast before touching data. A separate command with status and dry run was left for a later plan.
